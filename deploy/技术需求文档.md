## 一、项目背景

本项目是在 **Polymarket**（加密货币预测市场平台）上进行 **英雄联盟（LoL）比赛小局胜负市场** 的自动化交易。

核心逻辑：在比赛进行中，当某支队伍的赔率跌到特定阈值（表明市场过度悲观），且战局数据满足一组过滤条件时，自动买入该队伍的获胜代币。

**已完成的工作**（开发者不需要重做）：
- 历史数据分析（240局）
- 交易规则量化建模，保存在 `data/rules/trading_rules.json`
- 两个关键 API 已验证可用（见第三节）
- 市场列表数据已采集，保存在 `data/game_winner_markets/`

## 四、市场匹配逻辑

**核心问题**：将直播中的 LoL 比赛（已知队名 + 日期）匹配到 Polymarket 上对应的 token_id。

**已有数据**：
- `data/game_winner_markets/game_winner_markets.json`：2,700 个市场，包含队名和 token_id
- `data/game_winner_markets/game_start_times.json`：236 局的 game_id ↔ token_id 映射

**匹配方法**：
1. 从 LoL API 获取直播比赛的队名（如 `T1`, `KT Rolster`）+ 比赛日期
2. 在 `game_winner_markets.json` 中按队名 + 日期模糊匹配（已有 `difflib` 实现）
3. 匹配成功 → 得到 `token_0`（队伍A的代币）和 `token_1`（队伍B的代币）
4. 通过 `last-trade-price` 判断哪个 token 当前价格更低（弱势方）

## 五、交易规则（信号引擎逻辑）

规则完整版保存在 `data/rules/trading_rules.json`，核心逻辑如下：

### 5.1 入场条件（全部满足才触发）

```python
def should_enter(game_min, underdog_price, gold_diff, opponent_dragons, league):
    # 条件1：时间窗口
    if not (17 <= game_min <= 30):
        return False, "时间窗口不符"
    
    # 条件2：赔率阈值
    if underdog_price >= 0.30:
        return False, "赔率未触底"
    
    # 条件3：金币差（弱势方金币差不超过3000）
    if gold_diff < -3000:
        return False, "金币差过大"
    
    # 条件4：对方龙数
    if opponent_dragons > 3:
        return False, "对方龙数过多"
    
    # 条件5：联赛过滤
    if league not in ["LCK", "LEC", "LPL", "LCS"]:
        return False, "非目标联赛"
    
    return True, "触发买入"
```

### 5.2 仓位计算

```python
def calc_position_size(bankroll, underdog_price):
    if underdog_price < 0.10:
        return bankroll * 0.0075   # 彩票型：0.75%
    elif underdog_price < 0.20:
        return bankroll * 0.015    # 深度型：1.5%
    else:
        return bankroll * 0.025    # 标准型：2.5%
```

### 5.3 出场规则

```python
# 检查是否应该部分止盈（每次轮询时执行）
def check_exit(position):
    current_price = get_current_price(position.token_id)
    
    # 涨到买入价 3 倍：卖出一半
    if current_price >= position.entry_price * 3 and not position.half_sold:
        sell_half(position)
    
    # 游戏结束：自动结算（Polymarket 自动处理，无需操作）
```

### 5.4 每日风控

```python
MAX_DAILY_LOSS = float(os.environ.get("MAX_DAILY_LOSS", "50"))
```

## 六、运行模式

系统必须支持三种模式，通过环境变量切换：

```bash
DRY_RUN=true        # 模拟模式：只记录信号，不实际下单（用于测试）
DRY_RUN=false       # 全自动模式：满足条件自动下单
HUMAN_LOOP=true     # 人机协作模式：见下方说明
```

### 人机协作模式（HUMAN_LOOP）

**背景**：量化条件（金币差、龙数等）是统计规律，不是铁律。有时候单个指标超出阈值，但结合其他主观信号（队伍求生心态、反击点英雄状态等）依然值得买入。全自动模式会错过这些机会，人机协作模式解决这个问题。

**逻辑**：

```
条件全部满足  →  直接自动下单（同全自动模式）

条件部分满足  →  发送提醒给用户（Telegram / 终端提示）
（边界案例）     提醒内容包含：
                 · 当前赔率、游戏时间
                 · 哪个条件未满足（金币差 / 龙数 / 时间窗口）
                 · 当前战局快照（金币差数值、龙数、比分）
                 ↓
                 用户在 60 秒内回复 Y / N
                 Y → 系统下单
                 N / 超时 → 跳过，记录日志

条件全部不满足 →  静默跳过，写入日志
```

**提醒消息格式示例**：
```
⚠️ 边界信号 · LCK T1 vs KT · Game 2
游戏时间：21分钟
T1 赔率：28¢  ← 满足
金币差：-3800  ← ⚠️ 略超阈值（规则：>-3000）
对方龙数：2   ← 满足
─────────────────
60秒内回复：
Y = 买入 $12.5
N = 跳过
```

**记录要求**：用户的每一次 Y/N 决定都必须写入日志，供后续分析「哪些边界案例值得放宽规则」。这是未来训练机器学习模型的数据基础。

## 十二、注意事项

1. **私钥安全**：私钥只从环境变量读取，绝对不能出现在代码或日志里
2. **默认模拟模式**：`DRY_RUN` 默认为 `true`，需要客户手动改为 `false` 才能真实下单
3. **SSL**：LoL API 和 Livestats API 需要 `verify=False`（已知问题）
4. **容错**：单次 API 超时或失败不能终止程序，应 retry 3次后跳过本次轮询
